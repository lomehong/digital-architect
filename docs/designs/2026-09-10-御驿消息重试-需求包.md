## 2. 范围（Do）

- 盘点 dsh-yuyi 现状：`src/core/hub-client.ts`、`src/service.ts`、`src/tools/messaging.ts`、`src/core/inbox.ts`、`src/core/sent-ledger.ts`、`src/core/reply-loop.ts`；
- 界定「消息重试」的语义边界——**重试什么**（send ack 超时 / ack ok=false「delivery to X timed out」/ 断连在途 send / 未连接时发送）与**不重试什么**（Hub 明确拒绝、close 4008/4009、trace 类 best-effort）；
- 与御驿教程 §3.8.2 / §4.1.4 的契约对表，区分「协议已保证」（at-least-once 收件、message.id 幂等）与「端侧缺位」；

- 在 Q3=C 取向下给出结论与候选方案建议清单（持久化 / 可查 / 显式重发三段的最小形态与代价）。

## 3. 不做项（Don't）

## 8. 现状速查（证据表——「当前行为以代码为准」）

### 8.1 已有能力

| 能力 | 行为 | 证据 |
|---|---|---|
| 连接重连 | 指数退避 1s→30s；welcome 15s 超时后关闭重连；内部自动重连复用同一实例（roster 保留） | `src/core/hub-client.ts` `scheduleReconnect()` / `ws.onopen` 计时器 |
| 强制下线 | close 4008 / 4009 → 置 `closed`，**停止重连**（防连接风暴） | 同上 `ws.onclose` |
| 半开检测 | 应用层心跳 30s（`inbox/fetch {limit:0}`，兼保活 + 未读探测）；连续 3 次失败主动断开重连 | 同上 `startHeartbeat()` / `HEARTBEAT_FAIL_LIMIT=3` |
| 心跳统计 | 每 5 次心跳向 Hub 上报 ok/fail（`hb_stats` 特性，best-effort） | 同上 `maybeReportHeartbeatStats()` |
| 握手失败 | 无 welcome 15s → 关闭重连 | `REQUEST_TIMEOUT_MS` 计时器 |
| 发送 ack 关联 | `send()` 单次 request/ack 关联；`ack.ok===false` → `YUYI_SEND_REJECTED` | `src/core/hub-client.ts` `send()`；`src/service.ts` `dispatch()` |
| 等回复闭环 | `expectReply`：pendingReplies 先于发送注册（防漏收）；`replyTimeoutMs`（默认 300s）超时 `YUYI_REPLY_TIMEOUT`；可 abort | `src/service.ts` `sendExpectingReply()` |
| 接收侧 at-least-once | hub 侧不 ack 即重投；`yuyi_inbox target=hub` drain 后立即 `inboxAck` | 教程 §3.3.7；`src/tools/messaging.ts` `yuyi_inbox` |
| 唤醒投递 | notify 命中 idle 会话 → `agent.followup`（唤醒）；运行中 → `agent.steer`；mail / 无匹配 → 停靠收件箱 | `src/service.ts` `deliverToEntry()` / `routeDelivery()` |
| 出站账本 | `~/.yuyi/sent-messages.jsonl` 记「哪条出站消息是哪个窗口发的」，**仅用于回信锚定**，不驱动重发；超 1MB 裁到 2000 行；I/O 失败静默 | `src/core/sent-ledger.ts` |
| 任务记忆幂等 | request/reply 事件落 `~/.yuyi/tasks/<id>.jsonl`，msgId 幂等 | `src/core/reply-loop.ts`（`resolvedKey` / `appendTaskRecord`） |

### 8.2 缺口（重试相关）

| # | 缺口 | 触发条件 | 后果 | 现有兜底 | 证据 |
|---|---|---|---|---|---|
| G1 | **发送侧无重发** | ack `ok=false`（Hub 侧 ACK_TIMEOUT_MS=15s 超时）或 request 15s 无响应 | 出站消息在发送方视角丢失；工具报错后由模型决定是否重发（**无自动重发、无待发队列**） | 工具把错误抛给模型；`message.id` 已是幂等键，重发语义上安全 | `hub-client.ts` `request()`；`service.ts` `dispatch()`；教程 §3.8.2 |
| G2 | **无 outbox**：未连接即失败 | 断连窗口中调用 `yuyi_send` | 直接 `YUYI_NOT_CONNECTED`，消息从未进 Hub，无排队补发 | 无 | `service.ts` `requireConnected()` |
| G3 | **断连在途请求被拒** | WS 关闭瞬间的在途 send | `failAllPending("hub connection closed")` 全部 reject —— 无法区分「Hub 未收到」与「Hub 已投递但 ack 丢失」 | 无 | `hub-client.ts` `ws.onclose` |
| G4 | **接收侧无持久 msgId 去重** | drain 与 ack 之间进程崩溃；或本地 inbox 重复投递 | Hub 重投同一 msgId → 可能重复处理/重复回复 | 任务记录层 msgId 幂等（仅当消息带 taskId）；本地 `inbox.json` 无去重 | `src/core/inbox.ts`（模块注释明示本文件只服务单机/本机会话，无去重）；教程 §4.1.4 / §8.3 要求端侧持久化 msgId |
| G5 | **自动回执/自动回报无重试** | `autoAcknowledge` / `autoReport` 发送失败（恰逢断连或超时） | 仅 `logger.warn`；发送方要等 `replyTimeoutMs`（默认 5min）超时才收敛为 `YUYI_REPLY_TIMEOUT` | 无 | `service.ts` `autoAcknowledge()` / `watchTurnResult()` / `autoReport()` |

> **Q3=C 的落点预告**（评估阶段展开）：G1/G2/G3 的「不可见」部分可由「未 ack 出站消息持久化 + 可查 + 显式重发入口」覆盖，且不必触碰自动重发；G4 属**接收侧去重**，与本需求同域但不同缺口，评估需明确是否纳入结论范围。

### 8.3 真实环境佐证（非本仓，同协议实测）

| 现象 | 数据 | 来源 |
|---|---|---|
| 心跳时刻反复断连 | `close 1006 (abnormal closure)`，退避序列 1s/2s/4s/8s/16s/30s，多轮 | 本机 `C:\Users\hz0704027.OA\.yuyi\zcode-daemon.err.log`（2026-08-13，ZCode Go adapter） |
| 收件箱积压 | 对端观察「邮箱有积压（2→3 封）」 | 同上 `[deliver]` 行 |
| Hub 侧不重投即永留 | daemon 离线 1h 积压 50 条，重启后只接实时 deliver，堆积入箱无人拉（教程坑 #5） | `hub-plugin-doc.md` §5 坑 #5 |

> **有意的设计取舍（非缺陷）**：`hub-client.ts send()` 注释 C8 明确「message.id 是幂等键、请求 id 是关联键，重发同一消息必须保持 message.id」——说明重发被**预期由调用方完成**，只是当前没有实现重发的一方。评估需回答的正是「这个调用方应该是端侧插件，还是保持为模型/主人」——Q3=C 已给出方向：**保留给模型/主人，但把可见性补齐**。
