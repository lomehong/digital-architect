# Token 效率与人的反馈质量（Lessons 蒸馏）

## 教训一：避免廉价习得感

- 用 AI 写代码久了易产生「我也会编程」的错觉——**危险**：AI 写的代码人若不理解，就做不好审查，质量无从保障；
- 要求团队成员学基本开发概念（分层架构/ORM/中间件/SSE）——不是为了会写，而是**能看懂、能给出有质量的反馈**；
- 「这个函数职责太重，拆一下」「这个逻辑该放 service 层」「这个 SQL 没走索引」远比「感觉不对，再看看」有用；
- **AI 的输出质量 ∝ 人的反馈质量 ∝ 人对开发概念的理解程度**；不会写代码没关系，要能读懂大致逻辑。

## 教训二：给非开发者一张「能力地图」

- 用户侧同样有概念不清问题：不懂「导航栏/面包屑/抽屉」等产品语言 → 提需求沟通损耗大；
- 更关键：不知道**系统已经能做什么** → 要么重复提需求，要么不敢提；
- 解法：**能力地图**——一份结构化文档，把功能模块/Agent 能力/定时任务/开放 API 按业务域分类，每个能力一句话说明；AI 几分钟就能生成，成本极低；
- 效果：提需求明显「有的放矢」，能区分「已有能力的微调」vs「真正的新功能」，与 AI 对话的上下文描述更准确；
- **AI 原生研发要降的不只是「写代码」门槛，还有「理解产品」门槛**。

## 教训三：省 token 六法（+ 一个负结论）

1. **规则集中**（AGENTS.md 读一次即可，不到处重复约定）；
2. **工具返回 markdown 而非原始 JSON**——格式化表格约 200 token，原始 JSON 可达 10 倍；
3. **CLI 工具替代临时脚本**——一行命令 vs AI 写 50 行连接/执行/格式化代码；
4. **大仓 + 语义搜索**——一次会话覆盖全栈，减少「到处找文件」的探索开销；
5. **SDD 文档驱动**——复杂需求写成文档，AI 读完即有完整上下文，文档比对话历史精练；
6. **组件化 + Storybook**——先看 story 了解已有组件避免重复实现；组件小则单次改动上下文小。

**负结论（同等重要）**：RTK 类 token 压缩工具验证效果一般，偶尔压缩出 bug、压缩策略导致语义混淆——**弃用**；绝大多数 Bash 命令可通过参数精确控制输出，没必要为省几块钱引入一个不稳定的命令行代理。

## 本仓落点（适用范围）

- 与本项目「字节指标诚实结论」（蒸馏试点教训二）同调：**不引入重机制/不稳定工具换边际收益**；
- `architect_*` 工具输出已是 markdown 文本 ✓（互证）；
- **已落地**：为本生态生成一页「架构师 Agent 能力地图」（`docs/能力地图.md`，2026-09-11）——纯索引不复制，含五技能/门禁/知识资产/协同/入口五域 + 「暂无/挂起」清单；
- 审查侧启示：主人五问验收的价值取决于对方案概念的掌握——基线文档（metrics）与能力地图都是降低这一门槛的手段。
