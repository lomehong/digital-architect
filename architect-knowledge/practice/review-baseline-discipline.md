# 评审基准纪律：先锁定基准，再取证据

## 事故（OpsPi v1.4 评审）

方案声明「基于上游 pi（earendil-works/pi）扩展」。评审时本机**只有** omp（该血统的下游宿主）可用，于是评审者**把唯一可得的实现当成了契约标准**，逐条对照 omp 判方案的 API 断言，得出 **5 条错误结论**并据此给了「证据覆盖 3/10」的低分与驳回：

| 原判 | 事实（上游 pi 官方文档/类型） |
|---|---|
| `input` 事件返回 `{action}` 是虚构契约 | `{action:"transform"\|"handled"\|"continue"}` **正是** pi 的契约 |
| 自研审批门与宿主机制重复，应全交宿主 | pi **没有**审批子系统；官方文档把「确认 rm -rf 之类」列为**需要扩展自己实现**的用例 |
| 截断上限「2000 行」写错（应 3000）、自截断有害 | pi 文档原文 **"Tools MUST truncate their output"**，上限 **50KB / 2000 行**；3000 是 omp 的常量 |
| `import { Type } from "typebox"` 属 legacy 分支 | 这是 pi 官方 Quick Start 写法；"legacy/compat" 是 omp 对自家 shim 的标注 |
| `terminate` 不是契约字段 | `terminate?` 在 pi 契约中有文档语义 |

上游 pi 一直在 npm 上（`@earendil-works/pi-coding-agent`），取证据只需一次实装解包。**关键失误不是取不到证据，而是没去取就继续评分。**

## 纪律

1. **先确认基准，再取证据，再评分**。被评审对象声明了外部基准（上游项目、官方规范、行业标准）时，**必须取得该基准的可验证证据**（npm 实装解包 / 源码 checkout / 官方文档），再开始逐条核对。
2. **取不到基准证据 = 阻断，不是「标注 UNVERIFIABLE 后继续评分」**。带着未验证项评分，会把「基准不明」伪装成「方案有错」。
3. **「唯一可得」≠「标准」**。只有一个实现可用时，它只能证明「在该实现上的行为」，不能证明「契约应当如此」。评分口径必须写明基准是谁。
4. **别名的解析成功 ≠ API 面一致**。下游把上游包名重映射到自身体系（specifier alias）只说明**能加载**，不代表 API 语义相同——实测存在实质分歧（同一次评审中即发现 3 处）。
5. **分支/衍生类假设必须实测**。「A 是 B 的分支，故 B 的写法对 A 也成立」这类推断，每一处都要有实证或官方文档支撑。
