# 知识漂移案例与回写机制

> 知识最大风险是过期后「看似可信地误导 AI」。以下案例说明漂移如何被发现、如何处置。**处置公式：先修方案（以正确来源为准），再回写知识。**

## 案例一：知识库记「不排序」而代码已按权重排序（文章实证）

- **漂移**：知识库断言某链路不做排序；架构师 Agent 分析时照抄，方案与代码现实冲突。
- **发现**：设计核查阶段以**代码为准**核对当前行为，发现已按权重排序。
- **处置**：修正方案（尊重排序事实）；回写知识库条目并更新确认时间。

## 案例二：dsh-memory 存储路径知识失真（宪章 §5-02）

- **漂移**：文档/认知默认数据在各自插件目录；实际记忆库曾被放在 `~/.dsh/im-channel/credentials/`（兄弟插件目录 + 无视 DSH_HOME，多实例静默共享）。
- **发现**：宪章数据自治审计。
- **处置**：整改迁移到 `$DSH_HOME/dsh-memory/shared-memory.json`（旧路径自动迁移、旧文件留备份）；宪章登记册销账。

## 案例三：治理规则与真实工具面脱节（宪章自锁事故）

- **漂移**：「未知动作兜底 L2」规则在机制失效期间从未被真实检验；机制恢复运行即大面积误伤。
- **发现**：分身瘫痪（日常工作工具全被拦）。
- **处置**：闸改 opt-in + 探针常备；教训入册（修复失效安全机制前先审计它会拦截什么）。

## 案例四：提级规则误伤真实案例（task_delegate 关键词地板 v1→v2）

- **漂移**：规则假设「含删除类动词 = 破坏性」；真实任务「删除几行 DEBUG 打印」被误伤成 L3，任务永不执行。
- **发现**：真实任务卡死。
- **处置**：规则 v2 只对明确对外/破坏性词提级 + 执行反馈弹窗；**规则类知识变更必须带真实案例回归**。

## 案例五：套件根迁移致索引条目全面失效（2026-09-11 本仓实测）

- **漂移**：`reference/dsh-suite-architecture-map.md` 记的**三处设备绝对路径**（套件根 / 家目录 / 官方源码 checkout，Windows 盘符路径）**均已不存在**（旧路径残留为空目录）；成员清单缺 4 个新成员（dsh-model-failover / dsh-plugin-manager / dsh-remote / dsh-yuheng）。
- **发现**：v3 大脑/现场解耦走查中把容器 `TARGET_PROJECT` 指向旧路径 → workspace 为空 → 顺藤摸瓜核对三处路径的存在性与成员目录实况。
- **处置**：按本条目回写机制——条目标 `待审核`、正文加「⚠️ 漂移回写记录」、三处路径按实测更正、新成员入「待蒸馏区」（**能力未核不得引用**）、`source.ref` 补实测依据；主人确认后升级。
- **教训**：**路径类知识最容易无声失效**（改名/移动不报错，只在被引用时才暴露）；引用路径的知识条目应带「实测日期」，且跨仓路径迁移必须触发一次全库引用核查（可用 grep 全量扫旧路径）。

## 案例六：适配层文档声称的机制实际不存在（task-ledger 缺口，2026-09-12）

- **漂移**：`adapters/oh-my-pi.md` 与两个 SKILL（architect-design / architect-implement）均引用 `scripts/task-ledger.mjs` 作为 omp 侧任务面实现，但**全库检索无该文件**——文档描述了机制，机制从未建成。
- **发现**：OpsPi 方案落定后按流水线拆任务，需用 `create` 留痕；执行前核对落点，发现脚本不存在 → 无法留痕，只能人工搬状态（违反纪律二「一切知识进结构」与「机制优先于人工」）。
- **处置**：按 `principle/task-and-memory-surface.md` 的契约**实现**该脚本（五操作 + 四态状态机 + 四不变量；非法跳步、无来源 confirm、未落定归档均被脚本级拒绝），以 `--selftest` 覆盖 YAML 往返与状态机、`--validate` 做台账结构校验。**先修机制，再拆任务**。
- **教训**：
  1. **适配层文档属于「声明」，不是「证据」**——与代码/文件存在性冲突时以实测为准（同 `review-baseline-discipline` 的基准纪律）；
  2. **引用某机制的文档越多，缺失越隐蔽**（三处引用让缺口看起来像既有能力）；
  3. 引用外部机制的条目，宜附「存在性核对方法」（如 `ls scripts/task-ledger.mjs`），使缺口可被机械发现而非靠偶然撞见。

## 回写机制（本知识库执行细则）

1. 发现漂移：在条目 frontmatter 把 `status` 改 `待审核`，正文标注「与实证冲突」；
2. 修复方案：按事实类型回对应来源（当前行为→代码；业务意图→已确认知识；历史原因→实践记录）；
3. 回写：更新条目内容 + `confirmed` 日期 + 在 `source.ref` 补实证出处；涉及历史原因的新教训写入 `practice/`；
4. 重大规则变更（原则/流水线级）需主人确认后落定。
