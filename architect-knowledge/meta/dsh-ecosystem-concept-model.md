# dsh 生态概念模型

## 核心命题

**一个 dsh 实例 = 一个数字分身。** 这是理解套件内一切设计的元语。

- **主人（owner）唯一，分身是唯一执行主体**：主人通过对话、IM 渠道、任务看板安排任务。
- **实例级全局资产**（跨所有会话与渠道共享）：人设（四卡：身份/策略/样例/状态）、记忆（共享记忆库）、知识（种子 + 技能）、任务（看板）。
- **会话只是分身的多个「对话窗口」**：主人与访客看到的是同一人格的不同隐私投影，不存在按会话分裂的人格。访客可见性是一条红线（活动视图/完整 state 均不得注入访客）。

## 任务三层（职责互斥）

| 层级 | 载体 | 回答的问题 |
|---|---|---|
| 全局层 | 任务看板（dsh-task-board） | 分身有哪些任务、进展如何（主人视角） |
| 会话层 | harness tool-todo/goal/jobs | 这个会话里这一步怎么干（执行脚手架，随会话生灭） |
| 协同层 | 御驿任务链（dsh-yuyi 任务记忆） | 哪些活委派给了哪个远端协作者、干到哪了 |

## 治理与学习

- 分身对外行动受**委托账本 L0-L3** 约束（L2+ 人工审批 = 3 分钟令牌 + 今日待办批准 + 30 天授权）。
- 主人的批准/否决回流分身学习循环。
- **验收语义**：分身自报 ≠ 完成——task_report 自报后进「待确认」，主人在今日待办确认/驳回后才落定终态；确认的结果以「已验证结果（主人背书）」沉淀记忆。

## 知识定位（重要边界）

宪章 §0 决策：**分身的知识 = 种子化的权威事实记忆（dsh-memory）+ harness 技能，分身不另建个人知识库**。

边界澄清：本仓库 `architect-knowledge/` 是**架构师 Agent 的工程知识库**（业务/架构知识，服务技术方案设计），不是分身的第二个人格知识库，与宪章决策不冲突——分身 = 执行 Harness，SKILL + 知识库 = 架构师流程能力，挂在分身上（HANDOFF §4.3）。分析 dsh 生态需求时，两套知识面的分工：人格/任务/记忆语义查 dsh-memory 与宪章；工程架构事实查本知识库。

## 组织形态

套件是**插件联邦**——各成员共同实现上述模型，但彼此独立成活（联邦四原则见 `../principle/suite-federation-principles.md`）。
