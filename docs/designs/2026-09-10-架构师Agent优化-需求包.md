## 0. 文章深读：方法论完整地图

> 相对 dsh-memory 已入库蒸馏（`mem_1788978083156_yycfzp`），本次深读的**增量**集中在文章 §6.2~§8（此前条目以图 1/5/6/7/8 为主）。

### 0.1 主线

痛点（Context Gap →「局部正确、整体错误」）→ 四类断裂知识（业务/架构/服务内部/工程组织）→ 业界三路线（Spec-Driven / 长程 Harness / Agent-friendly Repo，均偏单服务，跨系统空白）→ 切入点=技术方案设计 → 两大建设面：**知识工程**（§5）与 **Agent Runtime**（§6.3）。

### 0.2 知识工程（§5）——第一层是领域不是 RAG

- 反 RAG 三论据：颗粒度不一致 / 语义相似≠工程相关 / TopK 无结构保证；第一性原理：**知识有结构宜结构化索引，信息松散才宜平铺检索**。
- business-knowledge 五类结构（meta/principle/scenario/practice/reference）+ 四个台账件：`index.md`（逐目录）、`review-queue.yaml`（待审核队列）、`source-manifest.yaml`（来源清单）、`evidence/images`（图示证据）。**蒸馏靠 skill 承载**：`business-knowledge-distill`（输入=技术方案/串讲/复盘文档，含图示下载与多模态解读）。
- 维护机制：日常增量（变更触发，未确认不得静默升级）+ 周期校准（大促/复盘资料）；每条知识带来源/确认时间/适用范围/状态/负责人。
- service-knowledge（§5.5）：与代码同仓或经 Harness/SKILL 关联均可；增量靠 git hook / coding-agent hook（已写进 AGENTS.md）；**YAML 高信息密度优于 markdown**；价值证据：>5 万行仓 code indexing 效率差一个数量级、多微服务扫描避免 context 压缩、实体/逻辑抽取省重复分析（≥25% 效率提升）。
- 渐进披露四层 + 回源纪律：当前行为以代码为准 / 业务意图以已确认知识为准 / 历史原因以实践记录为准；主动发现知识漂移（体验站三期「不排序」失真案、entrance 仓 grep 漏判案）。

### 0.3 Agent Runtime（§6.3）——五层结构

| 层 | 能力 | 解决什么 |
|---|---|---|
| a 业务理解层 | KBase MCP | 设计前是否理解需求背后的业务语义与领域上下文 |
| b 系统分析层 | AITOM（API 检索/调用关系/链路追踪） | 从入口探索真实链路与上下游，比单仓 grep 强 |
| c 架构推理层 | 技术方案设计 Skill | 固化工作方式：需求分析→分层加载→定位→覆盖验证 |
| d 服务知识层 | 各微服务 Service Knowledge | 服务级职责/契约/数据模型/依赖 |
| e 事实验证层 | Git Repository Code Context | 实现事实最终回源 |

Runtime 不是预加载大 Prompt，而是「发现问题→判断缺什么→定位来源→按需加载→继续推理」的动态环境；沿最短认知路径获得当前决策必需的上下文与证据。

### 0.4 设计执行（§6.4~6.6）

- 六步流程：读需求包 → 业务元语/场景解析 → 架构图谱定位链路（主路径/旁路/同步异步/红线）→ 按任务类型读服务知识并回源 Git → Gap 分析（复用/改造/新建，强迫回答「为什么这样做」）→ 生成完整方案。
- 人类角色转变：**从「替 AI 收集所有资料」转为「裁决事实缺口和承担关键决策」——人不再是系统知识的唯一检索器，而是知识质量和决策权的最终负责人**。
- 可执行方案标准（§6.5）：仓库范围与范围外参与方、术语对照与代码现状、复用/改造/新建 Gap、影响分析（调用方/异常传播/逐字节不变约束）、验证矩阵（不只单测）、未知显式登记——五问收口。
- 完备度度量（§6.6）：95% = 需求准入+知识可回源+代码核查+人工评审后的**六维度内容覆盖度**（非结构完整度）；剩余不确定性来自跨团队决策/外部系统/数据口径/产品取舍——本就不该由模型单独决定。

### 0.5 扩展路线（§7~8）

知识库是**多场景 Agent 基建**：方案设计（向未来推演）与线上排查（向过去回溯）共享元语/场景/图谱/服务知识四件套。从「技术方案设计 Agent」到「架构师 Agent」= 在同一底座上扩展需求增强、跨系统影响分析、架构评审、线上排查、Coding Agent 任务规划约束；**扩展方式=为 Agent 赋予对应 MCP（如 LogHouse、Service Runtime）**。三支柱分工：Skill 固化流程、Harness 组织上下文/工具/停止条件/证据校验、基模负责推理与动态编排。

## 2. 优化提案（分级）

| 级别 | 项 | 内容 | 可验收条目 | 成本量级 |
|---|---|---|---|---|
| **P0-1** | `knowledge-distill` SKILL | 把 `runbook-公众号采集.md` 泛化为蒸馏技能：输入=公众号文章/历史技术方案/串讲/复盘；流程=浏览器桥采集→图示解读→五类结构落库（`status: 待审核`）→登记台账 | 一篇新文章经 SKILL 全程蒸馏入库，四台账（source-manifest/review-queue/index/evidence）齐备且 knowledge-lint（P1-1）通过 | 纯文件，低 |

| **P1-1** | knowledge-lint（dsh-architect 扩展） | 纯函数：frontmatter 必填字段/`status` 枚举/`confirmed` 日期格式/来源可解析提示/review-queue 与 frontmatter 一致性；dsh 与 omp 双宿主导出，接两仓 CI | 校验器上线，存量条目全绿或问题清单清零；CI 红灯可阻断「结构漂移」 | 代码，中低（与既有 checker 同构） |
| **P1-2** | service-knowledge 试点 | 对 dsh-twin / dsh-task-board / dsh-memory 三仓生成 `.knowledge/`（YAML）+ `AGENTS.md` 路由 | 一次跨三仓影响面分析只读知识文件+定点回源即可完成；记录 token/时长对照，验证 §5.5 收益后再铺开 | 中（需读三仓源码） |
| **P2-1** | 完备度基线 | 对已落定 2 方案做六维度**内容**覆盖度人评（区别于结构分），登记 `docs/metrics`；后续方案逐单记录 | 基线表可回溯到每份方案；有下一次对比点 | 低 |
| **P2-2** | 架构图谱增维 | architecture-map 成员清单 → 增「调用关系/数据主责/一致性边界/强弱依赖」列（自宪章矩阵+源码蒸馏） | 覆盖 dsh-architect/dsh-yuyi/memory/task-board/twin 五核心件；条目带来源与确认时间 | 中 |
| **P3-1** | 需求增强职能（§6.2） | prd-digest 增「增强版 PRD」输出模式 | 模式定义 + 一次真实走查 | 待 federation 方案落定后另立包 |
| **P3-2** | 线上排查场景（§7） | scenario/ 新增排查场景映射（知识库第二场景复用） | 场景条目 + 一次真实复盘蒸馏验证 | 同上 |
