# 走查记录：omp 容器分层只读挂载

> 走查人：本建设会话 · 日期：2026-09-11 · 任务：TB-1789092914431-ij6n6（主人已批准）
> 背景：主人对「omp 知识/工具/skills 与 workspace 同权可写」提出异议——模型可写自己的规则面（SKILL/检查器），存在自我修改与提示注入放大风险。拍板方向：**不动目录布局，动挂载权限**。

## 变更

`docker/docker-compose.yml`：整仓挂载 `/workspace` 保持，追加 6 个只读子挂载覆盖——
`.omp`、`.claude`、`skills`、`dsh-architect`、`adapters`、`templates`（`:ro`）。
可写面保留：`architect-knowledge/`、`docs/`（蒸馏落库与方案产出的工作流写入面，由 review-queue + 主人确认 + git 历史兜底）。
更新路径：改仓库 → CI（G3 哈希守副本一致）→ `docker compose up -d` 重新生效。

## 过程发现

- **F1 密钥占位符事故**：容器重建时发现 `docker/.env` 的 `DEEPSEEK_API_KEY` 为占位符（旧容器 09-10 建时注入的是真实密钥，被覆盖丢失），首次 LLM 层验证 401。主人填回真实密钥后恢复。教训：`.env` 含占位符时 `compose up` 会静默用占位值顶掉运行中的好配置——建议后续 entrypoint 加 fail-fast（检测到 PLACEHOLDER 前缀即拒绝启动），登记不阻塞。
- **F2 残留风险（接受）**：知识库可写意味着被诱导的模型仍可污染知识条目，由 review-queue + 主人确认 + git 历史三道闸收敛；进一步收紧（知识库也 ro、写入走宿主侧看板任务）会改变蒸馏工作流，暂不采用。

## 结论

分层只读落地：**规则面模型不可改，工作面保留写入流**。与 G3 形成双保险——CI 管仓库内副本一致，ro 挂载管容器内不被篡改。
