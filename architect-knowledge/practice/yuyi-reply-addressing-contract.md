# 御驿回信寻址契约与闭环排障纪律

## 适用范围

凡通过御驿（Yuyi）Hub 做「请求-响应」闭环的 Agent 适配器与其运维：自动回信、手工回信、`expectReply` 请求、连接生命周期（close 码）。协议版本 v2；结论来自 2026-09-15/16 两台设备 omp 实例的真实故障与修复。

## 事故与现象

- 跨设备**自动回信 100% 被 Hub 拒**（ack `ok=false`），而同适配器的**显式发送**正常 → 表现为「手工发能到、自动回信必挂」；同设备对端回信却正常（约 13 次成功 vs 跨设备 5 次全败）。
- 端侧只显示成败文案（「回信发送失败…B 侧提示」），**Hub 的拒收原因不入日志** → 排查一度退化为猜测，最终靠 `yuyi_send` 的失败分支才掏出 Hub 原文。

## 根因：Hub 对「带 replyTo 的回信」有防伪造关联校验

**带 `replyTo` 的消息，其 `to` 必须能解析到「原请求发送方 agent」；解析单位是 `agent_name` / `agentId` / `sessionID`——会话别名不算（`device:别名` 也不算）。** 适配器回信帧的 `to.target` 取自发送方的**会话别名**（`msg.from.name`），故跨设备必被拒；同设备因别名可在本设备作用域解析而侥幸通过。

实测矩阵（同一条消息，仅改一个变量，均带真实 `replyTo`）：

| `to` 写法 | Hub ack |
|---|---|
| `agent_name`（裸名） | ✅ 接受 |
| `agentId` | ✅ 接受（文档未列该形式，实测可用） |
| `device:sessionID` | ✅ 接受（§3.5.1 合法 target） |
| 裸会话别名 | ❌ `回信去向与原请求发送方不符：目标 "…" 归属 agent (未解析)，原请求发送方为 <agentId>` |
| `device:别名` | ❌ 同上（**补设备作用域无效**） |
| 伪造 `replyTo` | ❌ `replyTo "…" 引用的消息不存在或未投递给本 agent（防伪造关联）` |

## 纪律（可复用结论）

1. **回信目标必须 agent 级**（`agent_name` / `device:sessionID` / `agentId`）；**裸别名与 `device:别名` 只适用于「非回信」的新消息**。适配器构造回信目标时应取入站消息的 `from.device` + `from.sessionID`，不要取 `from.name`。
   - 别名不可作长期寻址单位（**实测**）：同一设备上两个会话共用派生别名（`<device>-omp`）时，Hub 直接拒收——`投递失败：ambiguous target "…": PC-SZ-375:…, PC-SZ-375:…。请用 "设备名:别名" 或 sessionID 精确指定`。回信目标取 `device:sessionID` 可**免疫**该歧义；同设备多会话是常态（见下「初始化双连接/多会话」），故别名只应视作过渡期便利。
2. **回信永远带 `replyTo`（+ `taskId`）**：既是契约要求，也直接决定对端行为——对端入站分支对「带 `replyTo` 的消息」只做展示、不入队，因此不会触发对端（可能损坏的）自动回信；缺 `replyTo` 则被当成新请求。
3. **失败原因必须落日志**：适配器的回信发送必须记录 `ack.ok` / `deliveredAs` / `ack.detail`——**成功也要记**，否则「无失败日志」无法区分「成功」与「静默丢弃」。
4. **闭环排障先看 ack，再看端侧文案**：`ok:true` 不等于实时送达，要看 `deliveredAs`（`notify` = 实时；`mail_fallback` = 降级入箱）。
5. **close `4008`（管理员踢线）/ `4009`（replaced）不得重连**（防连接风暴）；`4008/4009` 之外（如 `1006` 异常断开、`4003` token 失效）仍按退避重连。置「不重连」标志后进程内无自动恢复路径，需宿主重启——运维需知情。
6. **上游构建件的本地补丁必须上游化**：`vendor/` 类整文件同步的产物，本地补丁在下次同步时**静默回退**；应把「回归夹具跑绿」当作同步后的检测器，并同时向上游报缺陷（本次走 Hub 文档评论通道）。
7. **验证判据要盖过最坏时延**：断言「不重连」的观察窗必须 > `重连退避上限 + jitter 上限`（本例 2000ms + 5000ms = 7s），窗口过短会产生**假绿**（危险方向＝回归漏检）。评审复跑基线时应多轮验证判据稳定性。

## 未知 / 待验证

- 对端为未升级适配器时其回信帧 `from.device` 为空串，此时 `to={device:"", target:<sessionID>}` 在真机能否解析——**已降级为理论分支**：`from.device=""` 只出现在回信帧，而这类帧本身会被 Hub 回信校验拒收、根本到不了接收方，故「回信给一个 `from.device` 为空的发送方」实际不可达（根治方向是端侧补 `from.device`）。残留未验证：**第三方适配器**若以空 `from.device` 直发普通消息（非回信）则可能触达，该来源未观测。
- `4009` 的真机触发源（文档称「已废、Hub 不再主动发」；评审提示还可能是同 token 多会话/初始化双连接）——**未验证**。
- **初始化双连接/多会话（跨节点复现）**：适配器初始化会 `connect()` 两次（工厂末尾 + `session_start`），产生一条僵尸 Hub 连接；两台设备（PC-SZ-375、sec-agent-manager-172-26-5-121）日志均可见「同 tick 两次连接」，疑为启动竞态。附带后果：同设备多会话共用派生别名 → 别名歧义（见纪律 1）。均**未定性、未修**。
