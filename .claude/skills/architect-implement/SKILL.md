# architect-implement · 开发执行流程

> **路径基准（v3.3，2026-09-11 主人拍板「开发状态/生产运行状态分离」）**：①知识库 `architect-knowledge/` 相对**大脑仓根**（omp=/opt/architect，仅 architect-knowledge 可写）；②**工作产出（方案/报告/执行记录）一律落目标项目 `docs/` 下**（designs/reports 分目录；自举场景目标项目=大脑仓本体）——大脑仓 docs 不再是生产产出落点；③模板/适配层相对大脑仓根（只读）。

你承担架构师 Agent 的**编码落地**职能（设计流水线的执行段）。前置条件：一份**已落定**的技术方案（主人确认）与任务号；执行方由主人点名（自编/委派规则见 `architect-knowledge/principle/coding-delegation-and-branch-discipline.md`）。**未落定的方案不得进入编码。**

## 流程

### 第一步：测试清单先行（先有验收后有代码）

1. 读方案「验证覆盖」维度，逐条转写为**可执行测试清单**（命令/脚本级，含预期观察）；
2. 读方案「需求覆盖 Do」与「系统覆盖」，把每条 Do 映射到将要改动的文件/配置；
3. 清单与映射写入执行记录（任务描述或 `docs/designs/<slug>-执行记录.md`）——后续每步对照它。

### 第二步：建分支（强制）

- 在**目标项目**内建 `feature/<任务号>-<slug>` 分支；主工作树保持只读基线；
- 跨仓任务在各自仓内各建分支，分支名带同一任务号（可追溯）；
- 分支建立后确认工作区干净（`git status` 为空）再动手。

### 第三步：小步编码与提交

- 每步只做一件事并立即验证：改代码 → 跑该步测试 → 绿灯才提交；
- **涉知识库改动时**：提交前必跑 knowledge-lint（按适配层：dsh=`architect_lint` 工具；omp=同名工具或 bash 兜底 `node /opt/architect/dsh-architect/scripts/lint-knowledge.mjs <KB根>`），error 非空不得提交；
- 提交信息中文，**注明改动归属**（如「方案 §2 系统覆盖：xxx 仓新增 yyy」）；
- **红灯不提交**——测试是交通信号灯；测试不通过时不得靠改测试绕过（除非测试本身错，且须在提交信息说明）；
- 不顺手重构、不夹带无关改动（方案外改动一律另记待确认）。

### 第四步：对照自检

逐条核对第一步的清单，输出三张表：

| 对照项 | 内容 |
|---|---|
| 方案对齐度 | 每条 Do 的落地点（文件:行）是否与方案一致；偏离必须说明 |
| 测试证据 | 每条验证手段的**实际执行输出**（命令 + 结果摘要），不得只写「已测试」 |
| 未兑现项 | 方案中未落地/降级/延期项，逐条显式登记（不得静默省略） |

需要结构分时，可用宿主检查器（`architect_design` 对方案、`architect_review` 对 diff+方案）辅助——但**机器分不等于实现质量**，对照表才是主证据。

### 第五步：停止条件（命中即停）

- **方案与现实冲突**（编码中发现方案判断错误/遗漏）→ 停：不在代码里私自改设计；登记冲突 → 走知识漂移流程 → 回 `architect-design` 修订方案；
- **涌现未知**（接口未定义、契约不明、跨团队依赖）→ 停并登记，**不得编造补全**；
- **触及治理面**（push、发布、删除数据、对外承诺）→ 停：按宿主适配文件走审批（dsh=账本 L2+ 今日待办；omp=强制 `ask` 主人，无账本不得静默放行）；
- **超范围**：发现需要改方案外文件 → 停，列入待确认。

### 第六步：自报与验收

1. 任务面 `report` 自报（实现按适配文件映射：dsh=看板 task_report / oh-my-pi=`scripts/task-ledger.mjs report`）：**diff 摘要 + 测试证据 + 未兑现清单 + 分支与 commit 范围**；
2. **自报 ≠ 完成**：实现评审（`architect-review` 实现评审模式，由非编码会话执行更佳）→ 主人确认 → 方可合并主分支/交付；
3. 合并后经验回灌 `architect-knowledge/practice/`（走待审核流程）。

## 浏览器验收任务（browser-acceptance，2026-09-25 落定）

验证覆盖中「像人一样打开浏览器操作系统」的验收类条目，执行手段为本仓 `browser-acceptance/` 能力包
（jev-ultrafast + 本地 Laya 决策服务 + 独立 Chrome，全链路无数据出域；用法与部署以 `browser-acceptance/README.md` 为准）。

- **清单写法**：验收类条目转写为 `run_acceptance.py` 调用——`--url/--goal/--allow-host/--expect-*` 四要素齐全才算可执行；
- **红线**：
  1. `--allow-host` 只许隔离环境/夹具主机，运行器无白名单拒绝启动；生产系统写操作验收禁止；
  2. 模型 DONE 自报不算证据，每条验收必须带 `--expect-*` 独立校验；截图/轨迹是附件，结论必须可复跑；
  3. 已知限制规避：搜索框打字、视口外元素（需先滚动）两类场景失败率高（Spike 基线 0/6）——验收目标改写为导航式表述，或登记为已知限制；
  4. 服务不常驻、不自启、不隐藏窗口；进程只杀登记 pid；
  5. 升级任何 pin 组件（`pins.yaml`）后必须复跑 `suite.py` 基线（导航类必须全过）；
- **缺席降级**：栈不可用 → 该条目退回 bash 单测/脚本验收（既有行为），流程不阻塞；
- **治理不变**：轨迹与判定落盘 `evidence/`，汇报引用路径；结果仍是自报证据，主人 confirm 才落定。

## 与既有 SKILL 的衔接

```
architect-prd-digest → architect-design → architect-review（方案评审）
   → 主人确认落定 → 【architect-implement】 → architect-review（实现评审）
   → 主人确认 → 合并/交付 → 经验回灌
```

## 纪律摘要

1. 未落定不编码；2. 无分支不开工；3. 红灯不提交；4. 证据要真实输出；5. 未兑现项必须显式；6. 发现方案错就停下来改方案，不在代码里偷偷改设计；7. 自报 ≠ 完成。
