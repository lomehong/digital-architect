# impl-discipline · 实现纪律

你承担**单票编码纪律**职能：在目标项目内按「先有验收后有代码」的顺序执行一张票——红绿循环推进，硬 bug 走诊断闭环，小步提交，对照自检后自报。

## 输入

- 一张票（含验收判据与可验收条目）；
- 目标项目（代码库、测试命令、分支纪律以其仓内约定为准）。

## 流程

### ⓐ 测试清单先行

票验收判据逐条转为**可执行命令级清单**（命令/脚本+预期观察）——「先有验收后有代码」。清单与「每条判据将落地的文件/配置」写入执行记录，后续每步对照。

### ⓑ 接缝预约定

测试只打**公共边界接缝**（seam）：写下接缝清单并经确认，未约定接缝不写测试；接缝本身存疑时停下对齐，不带疑推进。

### ⓒ 红绿循环

- 红**先于**绿：先写一个会失败的测试，再看它变绿；
- 一次一接缝一测试一最小实现；
- 垂直切片推进，防水平切分（反模式：全部测试先写完、再全部实现）；
- 重构不属循环——归评审段（`dual-axis-review`）。

### ⓓ 诊断闭环（硬 bug 六阶段）

1. **构建反馈环**：tight / red-capable / deterministic / fast——完成判据=一条**已实际跑过且能红**的命令；
2. **复现+最小化**：最小可复现样例；
3. **假设排序**：列 3–5 个可证伪假设，按可能性排序；
4. **单变量探针**：每次只动一个变量；调试日志打唯一前缀；
5. **修复+回归测试**：先红后绿；找不到正确接缝时，「无正确接缝」本身就是发现——登记，不硬造；
6. **清理**：按前缀 grep，探针日志清零。

**脱敏红线**：命令输出/工件先脱敏再示人（密钥、令牌、个人数据不出现在报告与提交物中）。

### ⓔ 小步提交

每步绿了才提交；提交信息中文、注明改动归属；**红灯不提交**——测试不通过时不得靠改测试绕过（测试本身有错须在提交信息说明）。

### ⓕ 对照自检

逐条核对 ⓐ 清单，输出三张表（映射 `architect-implement` 第四步）：方案对齐度 / 测试证据（**真实执行输出**，命令+结果摘要）/ 未兑现项（逐条显式）。

### 完成判据（两杠杆）

- **Clarity**：清单每条有**真实执行输出**（命令+结果摘要），无「已测试」空话；
- **Demand**：未兑现项逐条显式（静默省略=违规）+ 零夹带改动（方案外改动一律另记待确认）。

## 治理不变量（本技能语境的操作化；权威定义见 `architect-knowledge/principle/task-and-memory-surface.md` 与流程 K 各 SKILL.md）

| 不变量 | 在本技能中的生效方式 |
|---|---|
| 自报 ≠ 完成 | report 后仍须实现评审+主人 confirm 才能合并/交付 |
| confirm 归主人 | 交付确认归主人；评审意见不等于放行 |
| 治理动作不静默 | push/发布/删除数据/对外承诺 → 停+审批（沿 `architect-implement` 第五步停止条件） |
| 证据回源 | 清单每条附真实执行输出；证据可复现 |

## 与流程 K 的衔接

- `architect-implement` 的目标项目侧执行纪律：架构师自编时=implement 手段细化；委派执行方时=随票下发的纪律件；
- 流程 D 链路第四环：`ticket-split` 发布的每张票由本纪律执行（→ `dual-axis-review`）。
