## 0. 一句话与五问速答

| 五问 | 速答 |
|---|---|
| 改哪里？ | 各架构师 Agent 的知识仓新增 `federation/` 发布面（纯文件），三个 SKILL 增加「跨 Agent 装载」步骤，各 `adapters/<host>.md` 补「跨 Agent 共享」面；不改任何既有机制、不新增服务 |
| 为什么改？ | 多个架构师 Agent 各自掌握局部事实时，「局部正确、整体错误」会在 AI 与 AI 之间复现且冲突无声，需要协议层补齐人机之间的那套纪律 |
| 影响谁？ | 架构师 Agent 自身（新增跨 Agent 装载步骤）；既有套件机制（看板/账本/记忆/守卫）零改动；单 Agent 模式不受影响 |
| 如何验证？ | 静态字段校验 + 机械结构检查（复用 dsh-architect 纯函数）+ 双 Agent 场景走查（一致路径与冲突路径各一轮）+ 删目录即回滚 |
| 还有什么没有确认？ | 4 项：索引联邦形态、omp 侧通知落地方式、缺 owner 的补位顺序、裁决分级表未经真实案例回归 |

## 9. 附录 A：协议主干规范

### A.1 发布面目录结构（每个架构师 Agent 的知识仓内）

```text
federation/
├── manifest.yaml       本 Agent 身份：agent-id、owner、domains、host、capabilities、repo
├── index.yaml          对外发布索引（本仓分片，单一写者）：条目摘要 + 版本 + 状态
├── subscriptions.yaml  我关心谁的哪些面（按 key / facet / domain 模式声明）
├── peers.yaml          已知成员：agent-id、仓地址、宿主、可用通路、最近可见版本
├── changelog.yaml      append-only 变更流：谁、何时、哪个 key、版本变化、裁决留痕
└── contracts/          跨域契约条目全文
    └── domain.facet.name.md
```

### A.2 契约条目字段（共享的最小单元）

| 字段 | 必填 | 说明 | 示例 |
|---|---|---|---|
| key | 是 | 全局唯一，域.面.名 三段式 | dsh-yuyi.inbox.retry-policy |
| title | 是 | 一句话说明这条边界事实 | 御驿收件箱重试策略与上限 |
| facet | 是 | interface / data-ownership / consistency / version-constraint / shared-middleware / decision-constraint | interface |
| owner | 是 | 唯一写者（声明该边界的架构师 Agent） | architect-agent-dsh-suite |
| domain | 是 | 所属领域 | dsh-ecosystem |
| visibility | 是 | owner-only / team / public，默认 team | team |
| consumers | 是 | 反向索引：谁声明的依赖，显式空数组也要写明 | architect-agent-task-board |
| statement | 是 | 事实陈述 + 适用范围 + 不变量 | 收件箱重试三次后转人工，不丢弃 |
| source | 是 | 沿用既有来源字段：origin 与 ref | dsh-yuyi/src/retry.ts 第 42 行 |
| confirmed | 是 | 最后确认日期 | 2026-09-10 |
| status | 是 | 已确认 / 待审核 | 已确认 |
| version | 是 | 单调递增整数，禁原地覆盖 | 7 |
| supersedes | 否 | 被替代的前一版本引用 | dsh-yuyi.inbox.retry-policy 第 6 版 |
| verify | 是 | 怎么核对（当前行为以代码为准的路径） | dsh-yuyi/src/retry.ts 第 42 行 |

### A.3 冲突自动裁决分级表

| 冲突情形 | 裁决规则 | 是否自动 | 留痕方式 |
|---|---|---|---|
| 同一 key，来源等级不同 | 代码事实 高于 已确认知识 高于 实践记录 高于 待审核声明 | 自动 | changelog 记录败方降级与依据 |
| 同一 key，同等级，且该 key 有声明 owner | 声明 owner 优先，挑战方保留意见 | 自动 | 挑战方在本仓 practice/ 记 Conflict 条目 |
| 同一 key，同等级，且无 owner | 冻结使用（方案标注未决），登记 Conflict | 自动登记，不自动选择 | Conflict 条目 + 决策门升级主人 |
| 业务取舍 / 意图 / 跨团队承诺冲突 | 一律不自动 | 不自动 | 走六类决策门，决策记录入账本 |

### A.4 降级矩阵

| 缺失能力 | 降级行为 | 可发现性 | 恢复路径 |
|---|---|---|---|
| 兄弟索引不可达 | 影响面分析标注「边界未验证 N 项」，按保守侧收窄改动或停下问主人 | 方案系统覆盖区列出未验证项 | 通路恢复后重新校验版本并更新方案 |
| 无御驿（omp 侧） | 通知改为被动同步：拉取 changelog 与索引 | 通知面标注「被动同步」 | 接入御驿或改为定时拉取 |
| 无 git 通路 | 使用带 confirmed 时间的索引快照，过期阈值后视为无效 | 快照带日期与过期标记 | 恢复通路后重新拉取 |
| 契约条目缺 owner | 不可自动裁决，冻结使用并登记 Conflict | 方案中列出 Conflict 条目 | 主人或声明方补 owner 后解冻 |
| 宿主无共享记忆后端 | 以 git 条目为唯一权威，记忆面只做检索指针 | 适配文件标注该宿主记忆面为指针 | 宿主具备后端时补双写 |

### A.5 变更传播与新鲜度

| 机制 | 时机 | 做法 | 失败时 |
|---|---|---|---|
| 按需拉取 | 设计开始时（渐进披露第一层） | 拉取订阅面的索引分片，只读摘要不读全文 | 转入降级矩阵第一行 |
| 订阅通知 | 契约条目提交后 | 向 subscriptions.yaml 中声明关心的成员发提示，dsh 走御驿、omp 走被动同步 | 通知可丢，changelog 为唯一真相 |
| 新鲜度校验 | 每次读取契约条目 | 比对 index 与条目正文的 version 与 hash，不一致即重新拉取 | 不一致且无法拉取则标注未验证 |
| 版本留痕 | 方案定稿时 | 方案证据覆盖区记录所依赖契约的 key 与版本号 | 未记录版本的方案视为证据不完整 |
