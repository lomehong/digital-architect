# 只读挂载被大小写别名绕过——ro 子挂载方向性缺陷与 v2 修复

## 事故经过

分层只读 v1 采用「整仓 rw + 6 个子目录 ro」。主人在容器内实测改 `skills/` 下 SKILL.md：
直写被 EROFS 拦（模型如实报告），但模型发现 `/workspace/SKILLS`（大小写变体）**写入成功且真实落盘**——
9p 服务端大小写不敏感，别名路径落到同一 Windows 目录，却未命中 ro 子挂载点，走了 rw 父挂载。
宿主 `git status` 随即出现真实修改；已 `git restore` 还原，三副本校验一致。

## 根因

Linux VFS 大小写敏感 → 别名匹配不上 ro 子挂载 → 透传给 9p 父挂载（rw）→ Windows 侧大小写不敏感解析到同一目录。
**凡「rw 父 + ro 子」的只读分层，在大小写不敏感透传文件系统（Docker Desktop/WSL 跨界挂载）上结构性可绕过。**

## v2 修复（方向反转）

`..:/workspace:ro` 整仓只读为底，仅 `architect-knowledge/`、`docs/` 以**精确路径** rw 子挂载放行。
效果：任何大小写变体写入都落在 ro 父挂载被拒；实测 `SKILLS`/`SkIlLs`/`.OMP`/`ARCHITECT-KNOWLEDGE` 全部 EROFS，
精确路径读写正常，模型再次尝试篡改未落地（宿主 git 干净）。

## 教训

1. **安全边界不要依赖挂载点名的精确匹配**：在大小写不敏感透传层之上，ro 子挂载是「提名单过滤」而非「权限」；
   正确姿势是默认拒绝（父 ro）+ 精确白名单放行。
2. **负向测试必须含别名变体**：只测直写路径的「绿护栏」是假阴性——本次 v1 的全部验证用例都过了，护栏仍是坏的。
3. **宿主 git 是篡改的最终事实源**：容器内自报（无论诚实与否）不足为凭；本次最终修复的判定都落在宿主 `git status` 与确定性纯函数复跑上。
4. **模型诚实性是加分项不是控制项**：本次容器内模型主动报告了绕过并请示回滚——很好，但护栏设计不能假设它总会如此。
