## 0. 缺口清单（本需求包的输入）

深读代理逐文件走查（SKILL×4、知识条目 19 条、dsh-architect 源码、CI、基线表）发现的五项薄弱点：

- **G1 五问通过口径三处不一致**：`dsh-architect/src/coverage.ts` L166 `checkDesign` pass 要求 `fiveQuestions.answered === 5`；同文件 `renderReviewSkeleton` L187 文案为「五问作答 ≥4」；`skills/architect-review/SKILL.md` 只写「≥50 且无维度≤5」未提五问要求。
- **G2 根仓 CI 常态红灯**：`.github/workflows/ci.yml` L18-21 拉取私有 submodule `dsh-architect`，未配置 `SUBMODULE_TOKEN` 时 403——已登记为 U1（`docs/designs/2026-09-10-知识库机械校验-技术方案.md` §4），但红灯常态使「error 阻断」失去信号属性。
- **G3 SKILL 三副本手工同步**：`skills/` 与 `.claude/skills/`、`.omp/skills/` 三份副本，`adapters/oh-my-pi.md` L81 自认「改技能后需同步副本」，无校验机制——与知识库 R4/R5 防漂移防线自相矛盾。
- **G4 内容分自评偏差无机制收敛**：`docs/metrics/方案完备度基线.md` 文件头自认「评分者与方案作者同一会话」；rubric v1 无独立复核记录。
- **G5 占位符正则漏检英文**：`coverage.ts` L93 占位符识别仅覆盖含中文关键词的 `<...>`，英文占位符（如 `<TBD>`、`<description>`）漏检。

## 1. 可验收目标

1. G1：`coverage.ts` 的 pass 判定、`renderReviewSkeleton` 文案、`architect-review` SKILL 三处五问口径**一致**（以哪一档为准见 Q1）；变更带红绿测试用例回归（含「五问答 4 题」样本）；
2. G2：根仓 CI 在默认 secrets 配置下可跑绿（配置 token，或 CI 改为不依赖私有 submodule 的方案，见 Q2）；红灯恢复「异常信号」语义；
3. G3：`.claude/skills/`、`.omp/skills/` 副本由 `skills/` **生成或校验一致**（脚本或 lint R9），CI 中校验，副本漂移即红；
4. G4：基线表新增「复核者」列；至少 1 个既有方案由非产出会话复核一格并登记结果；rubric 增补复核规则（append-only，不回改历史行）；
5. G5：占位符检测补英文形态，带红绿样本测试；
6. 主人按五问验收（自报 ≠ 完成）。

## 2. 范围（Do）

- `dsh-architect`：coverage.ts G1/G5 修正 + 测试；lint.ts 增补副本一致性规则（R9，候选）；omp.ts 同步口径文案；
- 根仓：`.github/workflows/ci.yml` 修 G2；副本生成/校验脚本；`architect-review` SKILL 口径句修订；
- `docs/metrics/方案完备度基线.md`：增列 + 复核规则一行；
- 涉及知识条目的改动走漂移流程：条目标 `待审核` → 修正 → 主人确认后升级（`practice/knowledge-drift-cases.md` 回写机制）。

## 3. 不做项（Don't）

- **不改内容评分 rubric 的评分标准本身**（只加复核机制，不改分档定义）；
- **不做证据真伪的自动化校验**（source 字段真实性仍归评审抽查 + 主人确认——语义归人，方法论边界）；
- **不做 service-knowledge 蒸馏口径量化**（另一独立需求，不混入本包）；
- **不做 oh-my-pi 适配验收**（`adapters/oh-my-pi.md` status 待审核属主人验收动作，本包仅在其 G1 文案联动时同步）；
- **不建看板任务、不写分身记忆**（建设会话角色纪律）。
