# 自编/委派选择规则与编码分支纪律

## 一、自编 vs 委派（当前：主人点名制）

**规则（Q1 拍板）**：架构师自编或委派分身，由主人在方案落定、拆任务时**点名执行方**；架构师不自行判定、不争抢执行权。

- 默认不做自动判定（无阈值规则）——避免「规则假设」误伤（参见 `knowledge-drift-cases.md` 案例四教训：规则类知识变更必须带真实案例回归）；
- 待积累 3~5 个真实案例后，再复盘是否提炼默认规则（登记为 Unknown U1，复盘结论回灌本条目）；
- 无论自编还是委派，**验收语义不变**：自报 ≠ 完成，主人确认才落定。

## 二、编码分支纪律（Q3 拍板：强制）

1. **强制 feature 分支**：`feature/<任务号>-<slug>`；跨仓任务在各仓各建分支、分支名带同一任务号；
2. **主工作树保持只读基线**：不在主分支直接开发；开工前确认 `git status` 干净；
3. **小步提交**：一步一事，改动归属写进中文提交信息（对应方案条目号）；方案外改动一律不夹带，另记待确认；
4. **红灯不提交**：测试是交通信号灯；不得为过关而改测试（测试本身有错须在提交信息说明）；
5. **合并前置**：实现评审通过 + 主人确认后，方可合并或交付；试点期合并策略为 ff 保留 commit 链（可回滚优先，U2 待复盘）。

## 三、为什么这两条要进知识库

- 「通用编码素质」宿主自带（read/edit/bash/task/lsp/todo 等），但**流程合规性不会自带**——它属于本体系的纪律，必须显式成文并进 SKILL，否则每次靠模型自觉；
- 立项动机实测依据：本仓 2026-09-11 两次事故（ro 挂载别名绕过、手工同步漏提交权威源）均说明「默认拒绝 + 显式纪律 + CI 校验」优于「依赖自觉」。
